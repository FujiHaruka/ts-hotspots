# ts-dedup 要求仕様 (v1)

## 1. 目的とスコープ

ts-dedup は、GitHub Pull Request で変更された TypeScript コード片が、既存コードのどこかに Type-3 的に重複していないかを検出するツールである。

本ツールの位置づけは「正確な clone detector」ではなく、**リファクタリング検討に値する候補を高 recall で拾う detector** である。多少のノイズを許容し、最終判断は後段の coding agent / レビュアーに委ねる。

対象言語は TypeScript (`.ts` / `.tsx`) とする。

## 2. ステークホルダーとユースケース

- **コーディングエージェント**: PR 作成時に本ツールのレポートを入力として受け取り、重複に対するリファクタリング提案を行う。
- **レビュアー (人間)**: レポートを参照し、重複箇所の存在と根拠を確認する。

典型的なユースケースは、CI 上で PR に対して本ツールを実行し、検出された候補と根拠を構造化されたレポートとして出力することである。

## 3. アーキテクチャ概観

全体は次のパイプラインで構成される。各段階は入力を次段階に引き渡す単方向のデータフローをとる。

```
GitHub PR
  ↓
Diff Collector          … PR の差分を取得
  ↓
Codebase Indexer        … base branch の既存コードを索引化
  ↓
Changed Fragment Extractor … PR で変更された部分を周辺文脈ごと切り出す
  ↓
Feature Extractor       … 比較用の特徴量を抽出
  ↓
Candidate Search        … 索引から候補を高 recall で取得
  ↓
Similarity Scorer       … 候補ペアを再スコア
  ↓
Report Generator        … 構造化レポートを出力
  ↓
Coding Agent / Reviewer (下流利用者)
```

索引は PR ごとに CI 実行時にメモリ上で構築する想定であり、v1 では永続ストアは前提としない。

## 4. 機能要件

### 4.1 Diff Collector

- PR の base branch と head branch を受け取り、変更されたファイル・変更 hunk・変更行範囲を取得できること。
- 対象ファイルは TypeScript ソース (`.ts` / `.tsx`) のみとし、それ以外は後段に渡さないこと。
- 自動生成物・ビルド成果物・ベンダー配布物・ロックファイル・スナップショット・マイグレーション・大きなフィクスチャ等、重複検出の意味がないファイルを除外できること。除外ルールは設定可能であること。

### 4.2 Codebase Indexer

- base branch の TypeScript ソースを走査し、比較単位となる**コード片 (fragment)** に分割できること。
- fragment の粒度として少なくとも以下を扱えること。
  - 関数・メソッド・アロー関数の単位
  - `if` / `for` / `while` / `try` / `catch` / `switch` などの制御構造ブロック単位
  - 連続する文のウィンドウ (複数文にまたがる部分重複を拾うため)
- 各 fragment はファイルパス・行範囲・種別・ソーステキスト等、後段で参照・表示するために必要なメタ情報を保持できること。
- v1 では索引はメモリ上に構築すればよい。永続化は要求しない。

### 4.3 Changed Fragment Extractor

- Diff Collector が得た変更 hunk を含む fragment を抽出できること。
- 変更行のみでなく、変更行を包含する関数・ブロック・周辺の文ウィンドウまで含めて抽出できること。これにより関数全体の重複と部分的な重複の両方を検出対象にできること。

### 4.4 Feature Extractor

- fragment から比較用の**特徴量 (feature)** を抽出できること。v1 では少なくとも次の 3 系統を扱う。
  - **正規化済みトークン列の n-gram**: 識別子・文字列・数値・真偽値など意味のばらつきが大きいトークンを正規化した上で、局所的な並びを特徴とする。型注釈やコメントは基本的に無視する。
  - **文種別 (statement kind) の n-gram**: AST 上の文種別の並びだけを特徴とし、識別子差異に依存しない構造類似を捉える。
  - **呼び出し / プロパティアクセスの指紋 (fingerprint)**: 関数呼び出し名やプロパティアクセスなど情報量の高い要素は、識別子正規化とは別枠で保持する。
- 特徴量の粒度 (n-gram の長さ等) は調整可能であること。

### 4.5 候補検索 (Candidate Search)

- 4.4 で抽出した特徴量を転置索引として引ける形で保持できること。
- 変更 fragment の特徴量と一致する base fragment を、複数の特徴系統の **OR (和集合)** で列挙できること。高 recall を優先し、片方の系統だけでも一致すれば候補に含める。
- 候補ごとに、どの特徴系統でいくつ一致したかを集計できること。
- 変更 fragment 1 件あたりの候補件数は上限を設定可能であり、v1 では広め (数十〜数百件) に取ることを許容する。

### 4.6 類似度スコアリング (Similarity Scorer)

- 候補検索で得られたペアに対して、少なくとも次の観点で類似度を再評価できること。
  - トークン列の重なり
  - 文種別の並びの類似性
  - 呼び出し / プロパティの重なり
  - サイズの整合性 (極端に大きさが異なるペアを減点する)
- これらを重み付けした総合スコアを算出できること。重みは調整可能であること。
- 最終的に報告対象とするかは、総合スコアの閾値だけでなく、個別観点の閾値との **OR 条件**で判定できること。偽陰性を避けることを優先する。

### 4.7 レポート生成 (Report Generator)

- 検出された重複候補を、機械可読な構造化データ (JSON) として出力できること。Coding agent が直接消費できる形式とする。
- 1 件のレポート単位は **クローン群 (clone group)** とする。同じパターンが N 箇所に現れている場合、N 個のペアではなく 1 つの群として束ねて報告する。
- 1 件の群には、少なくとも次の情報が含まれること。
  - PR の base / head 識別子
  - 群の起点となるコード片 (anchor) の位置・種別・ソース。PR モードでは変更側 fragment、Whole-repo モードでは群を代表する 1 件。
  - 群の他メンバ (members) の配列。各メンバは既存側コード片の位置・種別・ソースに加え、anchor とそのメンバの間の総合スコア・個別観点のスコア・判定根拠を保持する。
  - 群レベルの集約スコア (`combined` および主要軸の `min` / `median` / `max`)。
  - 群全員に共通する判定根拠 (全メンバ間で共有される呼び出し・プロパティ・文種別・トークン n-gram)。
  - 群レベルの推奨ヒント (確信度、想定されるリファクタリング種別、注意フラグ)。

## 5. 振る舞いに関する要件

### 5.1 Recall 優先

- 本ツールは precision より recall を優先する。疑わしい候補は切り捨てず、スコアと根拠を付与した上で下流に委ねる。
- よって候補検索は複数特徴の和集合、最終判定は OR 条件を基本とする。

### 5.2 決定的な出力

- 同一入力 (同一の base / head、同一のコード状態) に対して、同一のレポートが得られること。ランキング順位も含め安定していること。

### 5.3 根拠の提示

- すべての報告候補について、なぜ類似と判定したかの根拠を人間にも機械にも読み取れる形で付与できること。スコアだけを出して終わりにしない。

### 5.4 役割分担の明確化

- 本ツールは「候補を広めに提示する」ことに責務を限定し、「採用 / リファクタリング実施」の判断は下流 (coding agent または人間) に委ねる。ツール側が自動的にコードを書き換えることはしない。

## 6. 全体の処理フロー

1. base branch をチェックアウトする。
2. TypeScript ソースをパースする。
3. base 側の fragment を抽出する。
4. base 側 fragment から特徴量を抽出する。
5. 転置索引を構築する。
6. PR head branch の差分を取得する。
7. 変更 hunk を含む fragment を抽出する。
8. 変更側 fragment から特徴量を抽出する。
9. 索引に対して候補検索を行う。
10. 候補ペアを再スコアする。
11. JSON / Markdown レポートを出力する。

## 7. 非機能要件

- **性能**: CI で実行可能な時間内に完了すること。v1 では全ペア比較は行わず、索引引きによる候補絞り込みを前提とする。
- **資源**: 索引はメモリ上に保持する。永続化やサーバプロセス化は v1 では要求しない。
- **決定性**: 同一入力に対して同一出力を返すこと (5.2 に同じ)。
- **拡張性**: 特徴量の追加・スコア重みの変更・除外ルールの追加が、パイプラインの他段階を書き換えずに可能であること。

## 8. v1 のスコープ外

次の項目は v1 では実装しない。将来バージョンでの検討対象とする。

- プログラム依存グラフ (PDG) に基づく完全な解析
- TypeScript 型チェッカに強く依存する高度な意味解析
- 埋め込みモデル (embedding) による類似度計算
- LLM を用いた類似度判定
- 永続化された索引 DB
- 全 fragment ペアに対する総当り比較
- 自動リファクタリングの適用

## 9. 設計思想 (補遺)

v1 は「広めに拾う → スコアと根拠を付ける → coding agent に判断させる」という役割分担で動くことを意図している。したがって、本仕様に対する実装判断で precision と recall がトレードオフになる局面では、原則として recall 側に倒すこと。
