v1 アーキテクチャ

目的は「PR で変更された TypeScript コード片が、既存コード内のどこかと Type-3 的に重複していないか」を高 recall で拾うことです。

GitHub PR
  ↓
Diff Collector
  ↓
Changed Fragment Extractor
  ↓
Feature Extractor
  ↓
Candidate Search
  ↓
Similarity Scorer
  ↓
Report Generator
  ↓
Coding Agent / Reviewer

1. Diff Collector

PR の差分を取得します。

入力:

* base branch
* head branch
* changed files
* changed hunks
* changed line ranges

対象はまず .ts / .tsx のみ。

除外候補:

* generated
* dist
* build
* vendor
* lockfile
* snapshot
* migration
* large fixture

2. Codebase Indexer

base branch の既存コードを走査して索引を作ります。

v1 では永続 DB なしで、CI 実行時にメモリ上で作ってもよいです。

既存コードを以下の fragment に分割します。

function / method / arrow function
block: if / for / while / try / catch / switch
statement window: 連続する 5〜20 文程度

各 fragment に ID を付けます。

type Fragment = {
  id: string;
  filePath: string;
  startLine: number;
  endLine: number;
  kind: "function" | "block" | "window";
  text: string;
  astNodeKind: string;
};

3. Changed Fragment Extractor

PR で変更された行を含む fragment を切り出します。

重要なのは、変更行そのものだけでなく周辺文脈も含めることです。

抽出するもの:

* changed hunk を含む最小 function
* changed hunk を含む最小 block
* changed hunk 周辺の statement window

これにより、関数全体の重複と部分重複の両方を拾えます。

4. Feature Extractor

各 fragment から検索用 feature を作ります。

v1 ではこの3種類で十分です。

A. normalized token n-gram
B. statement kind n-gram
C. call/property fingerprint

A. normalized token n-gram

TypeScript token を正規化します。

例:

identifier → ID
string literal → STR
number literal → NUM
boolean literal → BOOL
type annotation → optional/drop
comments → drop

その上で 3〜6 gram を作ります。

B. statement kind n-gram

AST の文種別だけを並べます。

例:

VariableStatement
IfStatement
ExpressionStatement
ReturnStatement

これを 2〜5 gram にします。

C. call/property fingerprint

呼び出しや property access は情報量が大きいので残します。

例:

CALL:findById
CALL:validateUser
AWAIT_CALL:client.get
PROP:user.id
PROP:response.status

識別子正規化とは別に、この特徴を持ちます。

5. Inverted Index

base branch 側 fragment の feature を索引化します。

type Posting = {
  fragmentId: string;
  filePath: string;
  startLine: number;
  endLine: number;
  featureKind: "token" | "statement" | "call";
};
type InvertedIndex = Map<string, Posting[]>;

key 例:

token:IF ID DOT ID
statement:IfStatement|ExpressionStatement|ReturnStatement
call:findById
prop:response.status

6. Candidate Search

changed fragment の feature を index に投げて候補を取得します。

ここでは recall 優先なので、複数 index の union を取ります。

token match
OR statement kind match
OR call/property match

候補ごとに feature hit count を集計します。

type Candidate = {
  changedFragmentId: string;
  baseFragmentId: string;
  hitCounts: {
    token: number;
    statement: number;
    call: number;
  };
};

上位 N 件を後段に渡します。
v1 では fragment ごとに 50〜200 件くらい広めに取ってよいです。

7. Similarity Scorer

候補ペアを再スコアします。

最低限この4つを見るとよいです。

tokenOverlap
statementKindSimilarity
callOverlap
sizeCompatibility

例:

score =
  0.40 * tokenOverlap
+ 0.30 * statementKindSimilarity
+ 0.20 * callOverlap
+ 0.10 * sizeCompatibility

偽陰性を避けたいので、最終判定は OR 条件を含めます。

report if:
  combinedScore >= 0.30
  OR tokenOverlap >= 0.35
  OR statementKindSimilarity >= 0.45
  OR callOverlap >= 0.40

8. Report Generator

Coding agent が読める JSON を出します。

type CloneCandidateReport = {
  pr: {
    baseSha: string;
    headSha: string;
  };
  candidates: Array<{
    changed: {
      filePath: string;
      startLine: number;
      endLine: number;
      kind: string;
      code: string;
    };
    existing: {
      filePath: string;
      startLine: number;
      endLine: number;
      kind: string;
      code: string;
    };
    scores: {
      combined: number;
      tokenOverlap: number;
      statementKindSimilarity: number;
      callOverlap: number;
      sizeCompatibility: number;
    };
    evidence: {
      sharedCalls: string[];
      sharedProperties: string[];
      matchedStatementKinds: string[];
      matchedTokenNgramsSample: string[];
    };
    recommendationHint: {
      confidence: "low" | "medium" | "high";
      likelyRefactoring: "extract-function" | "parameterize" | "manual-review";
      riskFlags: string[];
    };
  }>;
};

v1 の処理フロー

1. base branch を checkout
2. .ts/.tsx を parse
3. base fragments を抽出
4. base fragments から feature を抽出
5. inverted index を作る
6. PR head branch / diff を取得
7. changed hunks を含む fragments を抽出
8. changed fragments から feature を抽出
9. index で候補検索
10. 候補ペアを再スコア
11. JSON / Markdown レポート出力

v1 でやらないこと

最初はこれらは不要です。

* full PDG
* type checker 依存の高度解析
* embedding model
* LLM 判定
* 永続 DB
* 全ペア比較
* 自動リファクタリング

v1 の設計思想

v1 は「正確な clone detector」ではなく、
「リファクタリング検討に値する候補を高 recall で拾う detector」です。

そのため、多少ノイズが出てもよく、

広めに拾う
↓
スコアと根拠を付ける
↓
Coding agent に判断させる

という役割分担にするのがよいです。
