# M6: Report Generator (JSON + Markdown)

[docs/plans/milestones.md](./milestones.md) の M6 の実装計画。

## 目的

M4 までで得られた (score + candidate + features + fragments) を使って、coding agent と人間の双方が読める形に整形する:

1. **JSON レポート**: `CloneCandidateReport` (M0 定義) 形式。coding agent が構造化データとして消費する。
2. **Markdown レポート**: 人間が PR コメントで読める概要。

JSON には:
- PR の baseSha / headSha
- 変更側・既存側の position / kind / code
- combined と個別スコア
- evidence (共通する calls / properties / statement kinds / token n-gram サンプル)
- recommendationHint (confidence / likelyRefactoring / riskFlags)

## Approach

- **レポート生成は純粋関数**: 入力は `CandidateScore[]` + `Map<fragmentId, {fragment, features}>` + `pr: {baseSha, headSha}` + `config`。IO は呼び出し側 (M7) に委ねる。
- **evidence 生成**: M4 の `scoreCandidateDetailed` が返す intersections を使う。M6 側では intersections を受け取り、`sharedCalls` / `sharedProperties` / `matchedStatementKinds` / `matchedTokenNgramsSample` に分解:
  - calls 系 intersection を `CALL:`/`AWAIT_CALL:`/`NEW:` prefix で `sharedCalls` へ、`PROP:` prefix で `sharedProperties` へ振り分け (内部表現のまま expose)。
  - statements intersection は keys をそのまま `matchedStatementKinds` へ (例: `statement:IfStatement|ReturnStatement`)。
  - tokens intersection は keys の中から **先頭 K 個 (既定 5)** だけサンプルとして `matchedTokenNgramsSample` に入れる (全部出すと冗長)。サンプルはソート済みの先頭 K を使う (決定的)。
  - prefix (`token:`/`statement:`/`call:`) を落として人間向けにするかどうか:
    - v1 は **prefix を落とした素の表現で出す** (coding agent が読む時に context 無しで意味が通る)。
    - `call:CALL:findById` → `CALL:findById`
    - `statement:IfStatement|ReturnStatement` → `IfStatement|ReturnStatement`
    - `token:ID DOT ID` → `ID DOT ID`
- **recommendationHint の導出**:
  - `confidence`: combined score から
    - >= 0.7 → "high"
    - >= 0.4 → "medium"
    - その他 → "low"
  - `likelyRefactoring`:
    - token と statement が共に >= 0.7 かつ sizeCompatibility >= 0.6 → `"extract-function"` (機械的に共通部分を切り出せそう)
    - call が >= 0.5 かつ statement が >= 0.5 → `"parameterize"` (呼び出しパターンが似ており、引数化で統合できそう)
    - それ以外 → `"manual-review"`
  - `riskFlags`:
    - size 比が 3x を超える → `"size-mismatch"`
    - evidence.sharedCalls と sharedProperties が両方空 → `"low-semantic-evidence"`
    - combined < 0.3 かつ採用理由が個別観点の閾値越えだけ → `"threshold-based"`
    - changed と base が同一ファイル → `"same-file"`
  - riskFlags は決定的な順序で (辞書順昇順) 並べる。
- **レポート内のランキング順**:
  - 第一: combined 降順
  - 第二: max(tokenOverlap, statementKindSimilarity, callOverlap) 降順
  - 第三: changedFragment.id 辞書順 昇順
  - 第四: baseFragment.id 辞書順 昇順
- **同一 changed × 同一 base の重複除去**: M3 で (changed×base) ペアは 1 回しか出ないはずだが、将来の安全のため `Set<"${changedId}|${baseId}">` で dedupe。
- **code フィールド**: fragment.text をそのまま入れる。改行コードは LF のまま。
- **Markdown フォーマット** (人間向け、最小限):
  ```
  # ts-dedup report

  base: <baseSha>
  head: <headSha>
  candidates: N

  ## 1. src/changed.ts:12-34 (function) ⇄ src/existing.ts:5-30 (function)

  - combined: 0.78
  - token: 0.82, statement: 0.90, call: 0.60, size: 0.75
  - confidence: high / refactoring: extract-function
  - risks: size-mismatch

  shared calls: CALL:findById, AWAIT_CALL:client.get
  shared properties: PROP:user.id
  matched statement kinds: IfStatement|ReturnStatement
  matched token n-grams (sample): ID DOT ID, IF ID DOT ID

  <details><summary>changed</summary>
  <pre>...code...</pre>
  </details>
  <details><summary>existing</summary>
  <pre>...code...</pre>
  </details>
  ```

### API

```ts
import type {
  CloneCandidateReport,
  ReportCandidate,
  Evidence,
  RecommendationHint,
  Fragment,
  FragmentFeatures,
  CandidateScore,
} from "../domain/index.ts";
import type { Config } from "../config/index.ts";

export interface ScoredPair {
  score: CandidateScore;
  changedFragment: Fragment;
  baseFragment: Fragment;
  intersections: {
    tokens: string[];
    statements: string[];
    calls: string[];
  };
}

export interface ReportInput {
  pr: { baseSha: string; headSha: string };
  pairs: readonly ScoredPair[];
  config: Config;
}

export function buildJsonReport(input: ReportInput): CloneCandidateReport;

export function buildMarkdownReport(report: CloneCandidateReport): string;

export function buildEvidence(
  intersections: ScoredPair["intersections"],
  config: Config,
): Evidence;

export function deriveHint(args: {
  score: CandidateScore;
  evidence: Evidence;
  changed: Fragment;
  base: Fragment;
}): RecommendationHint;
```

### config 追加

M6 で使うサンプル件数 (token n-gram) を config に追加する:

```ts
// src/config/config.ts (既存を拡張)
report: {
  tokenNgramSampleSize: number;  // 既定 5
};
```

config 更新は M0 の config.ts / defaults.ts に 1 行ずつ追記する形で。M6 の実装時に追記する。

## テスト

### evidence.test.ts

1. calls intersection の `CALL:*` / `AWAIT_CALL:*` / `NEW:*` は sharedCalls へ、`PROP:*` は sharedProperties へ。
2. statements intersection は matchedStatementKinds にそのまま。
3. tokens intersection は prefix `token:` を剥がされ、先頭 K 件だけ残る。
4. 空 intersection → 全フィールド空配列。

### recommendationHint.test.ts

1. combined >= 0.7 → confidence "high"。
2. combined 0.4..0.7 → "medium"。
3. combined < 0.4 → "low"。
4. token/statement >= 0.7 かつ size >= 0.6 → "extract-function"。
5. call >= 0.5 かつ statement >= 0.5 (他は条件外) → "parameterize"。
6. どれにも当てはまらない → "manual-review"。
7. size 比 >3x → riskFlags に "size-mismatch" を含む。
8. evidence.sharedCalls + sharedProperties 両方空 → "low-semantic-evidence"。
9. 同一ファイル → "same-file"。
10. riskFlags は辞書順。

### ranking.test.ts

1. combined 降順で並ぶ。
2. combined 同値のとき max(token, statement, call) 降順。
3. 全スコア同値 → changedId 昇順 → baseId 昇順。
4. 決定性: 2 回実行で同じ順序。

### jsonReport.test.ts

1. pr.baseSha / headSha が入力通りに入る。
2. candidates の件数が入力と一致。
3. 各 candidate に changed/existing の filePath/startLine/endLine/kind/code が入る。
4. scores が combined + 4 観点で埋まる。
5. evidence が buildEvidence の結果と一致。
6. recommendationHint が deriveHint の結果と一致。
7. 決定性: 2 回実行で同一 JSON (JSON.stringify してから比較)。

### markdownReport.test.ts

1. 候補 0 件の場合でもヘッダが出て、`candidates: 0` を含む。
2. 候補 1 件以上の場合、スコア / hint / evidence / code ブロックが描画される。
3. 特殊文字 (`<`, `&`, バッククォート等) は markdown code block の中で壊れない (HTML エスケープは `<details>` の外のみ必要。code は `<pre>` を使うので生のまま)。
4. 決定性: 2 回実行で同じ文字列。

## リスク / 留意点

- **Evidence prefix の剥がし方**: 実装のメタ情報 (`call:`/`statement:`/`token:`) を report に残すか剥がすかは trade-off。v1 は剥がす (coding agent が文字列をそのまま参照すると意味が通る方)。
- **Markdown の改行**: 末尾改行は 1 個にする。GitHub の PR コメントでは `<pre>` を使うと code block がそのまま出る。
- **recommendationHint の規則**: 仕様は v1 では暫定で、M8 で実データを見て再調整する前提。テストは規則のコードから逆算するかたちで書く。
- **同一 changed fragment に対する複数 base**: report は candidate 単位で独立に出す (同じ changed に対して複数の existing が並ぶ)。ランキングで既に決定的順序。
