# M2: Feature Extractor 3 系統

[docs/plans/milestones.md](./milestones.md) の M2 の実装計画。

## 目的

Fragment (M1) から、検索・スコアリングで利用する 3 系統の特徴量 (feature) を抽出する:

- **A. normalized token n-gram**: 識別子・リテラルを正規化したトークン列の n-gram
- **B. statement kind n-gram**: 文ノードの kind 列の n-gram
- **C. call / property fingerprint**: 呼び出しとプロパティアクセスを正規化した指紋

最終的に、1 fragment → `FragmentFeatures { tokens, statements, calls }` を返す `extractFeatures` に集約する。

## Approach

- **Fragment.text を再パースするのではなく、fragment の範囲を含む SourceFile を先にパースしてから AST を絞り込む**方針を採る。理由:
  - fragment.text 単体はパース時に syntactic に半端 (例: `if (x) { ... }` だけなら OK だが、arrow body の expression 部分だけ切り出したりすると構文不整合を起こす)。
  - M1 は「元ソースの部分範囲」を fragment として持つので、M2 は「fragment 抽出と同じ SourceFile に対して該当範囲の node を特定し、そこから feature を取る」のが安全。
  - ただし M2 の公開 API は「fragment + sourceFile」を受け取る形にする。SourceFile の生成責務は M1 に任せる。
- **公開 API の形**: `extractFeatures(fragment, sourceFile, config): FragmentFeatures`。SourceFile が無い場合 (将来のユースケース) は fragment.text から再パースするフォールバックもあり得るが v1 では要求しない。
- **範囲内ノードの特定**: `ts.forEachChild` で SourceFile を走査し、`node.getStart(sf) >= fragmentStartPos && node.getEnd() <= fragmentEndPos` を満たす最上位 node を見つける。または、`astNodeKind` + `[startLine, endLine]` で該当 node を突き当てる。window は複数 statement の範囲なので「範囲に含まれる連続 statements」を集める。
- **トークン列 (A)**: `ts.createScanner(ScriptTarget.Latest, /* skipTrivia */ true, ts.LanguageVariant.Standard, text)` を使う代わりに、SourceFile のトークン列を AST から得るのが堅い。`ts.forEachChild` で TokenObject (Leaf) を集める方針を採るが、TypeScript API では葉トークンだけを集めるユーティリティが無いため、fragment の範囲に対してのみ `createScanner` を走らせる実装を採る:
  - `scanner.setText(sourceFile.text)` + `scanner.setTextPos(fragmentStartPos)` で該当範囲だけスキャン。
  - `scanner.setLanguageVariant(.tsx ? TSX : Standard)`。
  - `SyntaxKind.SingleLineCommentTrivia` / `MultiLineCommentTrivia` は skipTrivia=true で除外される。
  - 型注釈の除去: scanner は型注釈を通常のトークンとして吐くので、AST 側で「TypeAnnotation / TypeReference 配下の position」をあらかじめ除外リストにし、スキャン中に該当 position をスキップする。ただし v1 では **型注釈除去は簡易**に: `: Type` の `:` を検出したら次の "statement terminator" (`,`, `)`, `=`, `{`, `;`, `>`) が現れるまで token を捨てる粗いヒューリスティックで十分。完璧な除去は M8 で調整する。
    - さらにシンプルに: **AST で type node の範囲 (TypeNode の start/end) を先に収集して除外範囲セットにし、scanner のトークンがその範囲に完全に入っていたらスキップする** 実装に倒す。これなら確実。
- **正規化 (A)**:
  - `Identifier` → `ID`
  - `PrivateIdentifier` → `ID`
  - `StringLiteral` / `NoSubstitutionTemplateLiteral` / `TemplateHead` / `TemplateMiddle` / `TemplateTail` → `STR`
  - `NumericLiteral` / `BigIntLiteral` → `NUM`
  - `TrueKeyword` / `FalseKeyword` → `BOOL`
  - `NullKeyword` / `UndefinedKeyword` → `NULL`
  - `RegularExpressionLiteral` → `REGEX`
  - その他の keyword / punctuation: そのまま大文字化した名前を使う。具体的には `ts.SyntaxKind[kind]` を縮めた短縮形 (例: `IfKeyword` → `IF`, `OpenBraceToken` → `LBRACE`)。実装上は明示的な map テーブルを持つ:
    - 主要なものを列挙する mapping を定数テーブルで持ち、未登録 kind は `ts.SyntaxKind[kind]` をそのまま使う (fallback)。
  - n-gram 生成: 正規化済みトークン列 (string 配列) に対し、config.features.tokenNgramSizes (既定 [3,4,5,6]) の各 size で window を切り、joined (空白区切り) を key に。
  - FeatureKey: `token:${joined}`。

- **statement kind n-gram (B)**:
  - fragment のスコープ (function body / block body / window の statements 配列) に含まれる「直下の文」の `astNodeKind` (例: `VariableStatement`, `IfStatement`, `ExpressionStatement`, `ReturnStatement`) を深さ優先で集める。
  - **深さの扱い**: 制御 block の **直下の文** のみを並べる (flat リスト)。ネストされた if 内の文は内側 fragment の feature 側で拾うので、外側 fragment ではネスト node 自体 (`IfStatement`) を 1 要素として並べるに留める。これで外側と内側で feature が自然に分離する。
  - n-gram: config.features.statementNgramSizes (既定 [2,3,4,5]) で生成。
  - FeatureKey: `statement:${kinds.join("|")}`。

- **call / property fingerprint (C)**:
  - fragment 範囲の AST を再帰的に訪問:
    - `CallExpression`: expression が `Identifier` → `CALL:${name}`、`PropertyAccessExpression` → `CALL:${objectText}.${property}` (object は正規化した `ID` を使わず、簡易には **最後のセグメント名**のみ: `CALL:${expr.name.text}` とする)。ただし `this.foo()` / `a.b.c()` のような chain を区別するため、**左端識別子 + プロパティ最終名** の形 (`CALL:a.c`) に正規化する。
    - `AwaitExpression` が親にある場合は `AWAIT_CALL:` prefix にする (await を見分けるため)。
    - `NewExpression` → `NEW:${name}`。
    - `PropertyAccessExpression` が call の subject でない (参照として使われる) 場合 → `PROP:${lhs}.${name}`。左端識別子 + プロパティ名。
    - `ElementAccessExpression` はキーが文字列リテラルなら `PROP:${lhs}.${key}`, それ以外は `PROP:${lhs}.*`。
  - 同じ fingerprint が複数回出ても bag として重複を残す (count に意味がある)。
  - FeatureKey: `call:${fingerprint}` (prefix を call に統一、PROP / CALL / NEW / AWAIT_CALL の内部区別は後続の value 部で表現)。

- **normalize 方針のシンプル化**:
  - 左端識別子の取得は `ts.PropertyAccessExpression` を再帰的に降りて最深の `Identifier` を返すユーティリティに切り出す。
  - `this` / `super` はそのまま使う (識別子正規化の対象外; 情報量を残すため)。
  - 意味がとれない (computed key が complex expression) のケースは `*` で fallback。

## テスト

### normalizedTokenNgram.test.ts

1. 識別子だけ変わった 2 つの関数の 3-gram が大部分一致する。
2. string / number / boolean / null / regex のリテラルがそれぞれ `STR` / `NUM` / `BOOL` / `NULL` / `REGEX` に正規化される。
3. 型注釈が除去される: `const x: number = 1` と `const x = 1` が同じ n-gram 列。
4. コメントが無視される。
5. n-gram size を config で 2 に狭めると、生成される key が短い並びになる。
6. 決定性: 同一 fragment → 同一 key 列。

### statementKindNgram.test.ts

1. 関数内の `VariableStatement, IfStatement, ReturnStatement` から `statement:VariableStatement|IfStatement` 等の 2-gram key が出る。
2. 識別子やリテラルが違っても statement kind が同じなら同じ key が出る。
3. 深いネストは直下の文だけを拾い、ネストノード (`IfStatement`) は 1 要素として扱う (外側 fragment 視点)。
4. 文が少ない場合は該当 n-gram size で出力が空になり、size を下げれば出る。

### callPropertyFingerprint.test.ts

1. `findById(x)` → `call:CALL:findById` が出る。
2. `await client.get()` → `call:AWAIT_CALL:client.get` が出る。
3. `response.status` (参照) → `call:PROP:response.status` が出る。
4. `new UserRepo()` → `call:NEW:UserRepo` が出る。
5. `a.b.c()` → 左端識別子 + 最終 property で `call:CALL:a.c`。
6. `this.foo()` → `call:CALL:this.foo` (this はそのまま)。
7. `obj["key"]` → `call:PROP:obj.key`。`obj[i]` → `call:PROP:obj.*`。

### extractFeatures.test.ts

1. 3 系統全てが詰まった `FragmentFeatures` を返す (tokens, statements, calls が非空)。
2. 同一 fragment を 2 回渡すと同じ結果 (決定性)。
3. 空の関数 body でも crash せず、全て空配列を返す。

## リスク / 留意点

- **TypeScript の型注釈除去**: 完全除去には AST による TypeNode 範囲取得が必要。簡易ヒューリスティックだと `:` の誤検出 (例: object literal shorthand の `{ a: 1 }`) で過剰除去になる。v1 は AST ベースで行う。
- **normalize テーブルの抜け**: 未登録 SyntaxKind は `ts.SyntaxKind[kind]` をそのまま使い、fallback で対応する。これなら抜けても決定性は保たれる。
- **fingerprint の粒度**: `a.b.c()` を `CALL:a.c` と潰すと `foo.c()` と `bar.c()` が同じ fingerprint になる。recall 優先の方針とは合致するが、false positive が増える局面は M8 で評価。
- **window の範囲**: window は複数 statement にまたがる範囲なので、M2 の feature 抽出は「範囲に完全に含まれる AST node」を拾う必要がある。範囲外に出ていく node (親 block) は含めない。
- **tsx**: scanner に `LanguageVariant.JSX` を渡す必要あり (`.tsx` ファイルの fragment に対して)。filePath の拡張子から決定する。
