# M7: CLI 統合と E2E

[docs/plans/milestones.md](./milestones.md) の M7 実装計画。

## 目的

M1〜M6 をひとつのパイプラインに配線し、`ts-dedup` コマンドとして実行できる CLI を完成させる。
実装内容と小規模 fixture repo を使った E2E テストで、PR 差分 × 既存コードの重複検出が
「期待されるペアを少なくとも 1 件拾う」ことを確認する。

## Approach

### 全体の形

- **パイプライン本体は純粋関数 `runDetector`** に閉じ込める。
  - 入力: `{ repoPath, baseRef, headRef, config }`
  - 出力: `{ report: CloneCandidateReport, stats }`
  - E2E テストは `runDetector` を直接呼び、argv パースや fs 書き出しを経由しない。
    CLI 層のバグとパイプラインのバグを切り分けやすくするため。
- **CLI 層** (`src/cli/main.ts`) は薄く保ち、argv パース → `runDetector` → 書き出し
  だけを担当する。
- **base 側のコード列挙**は worktree ではなく `git ls-tree -r <baseSha>` を使う。
  head 側 fragment と同じく worktree に依存させないことで決定性を担保する。

### `runDetector` の内部フロー

1. `collectChangedFragments` (M5) で `baseSha`/`headSha`/変更ファイル + 変更 fragments を取る。
2. `listBaseSources(repoPath, baseSha, config)` で base branch に存在する
   `.ts`/`.tsx` ファイルを列挙し、除外 glob を適用し、`git show` で本文を取る。
3. base の各ソースを `parseSource` → `extractFragments` → 各 fragment ごとに
   `extractFeatures` の順で 1 回走査する。1 周で
   - `baseEntries: { fragment, features }[]` (index 構築用)
   - `fragmentById: Map<string, Fragment>` (re-score 用)
   - `featuresById: Map<string, FragmentFeatures>` (re-score 用)
   を同時に作る (ソース毎に `sourceFile` を使い回せて効率的)。
4. `buildInvertedIndex(baseEntries)` で転置索引を構築する (M3)。
5. head 側の changed fragments を処理する:
   - changed file ごとに 1 度だけ `parseSource` を呼んで `sourceFile` を得る。
   - 各 changed fragment に対して `extractFeatures` → `searchCandidates` →
     候補ごとに `scoreCandidateDetailed` → `shouldReport` で採否。
   - 合格した (changed, base) ペアを `ScoredPair[]` に詰む。
6. `buildJsonReport` (M6) で `CloneCandidateReport` を作る。
7. オプションで `buildMarkdownReport` も生成。

注: 同一 base file の「changed 版」と「base 版」はどちらも index に現れる
(base 版が index に入り、head 版は changed fragment として別 id を持つ)。
この場合、強くマッチして report に出得るが、`deriveHint` で `same-file`
riskFlag が立つため下流で deprioritize できる。M7 段階では追加フィルタを
入れず recall を優先する (M8 で再検討)。

### CLI 引数

- 使う parser: `node:util.parseArgs` (node 18.3+)。新規 npm 依存は追加しない。
- オプション:
  - `--base <ref>` (必須): base ref / sha。
  - `--head <ref>` (必須): head ref / sha。
  - `--repo <path>` (任意): git リポジトリのパス。既定は `process.cwd()`。
  - `--out <path>` (任意): JSON の出力先。省略時は stdout。
  - `--markdown <path>` (任意): Markdown の出力先。指定時のみ書き出す。
  - `--help`: usage を stderr に出して exit 0。
- 終了コード: 検出ゼロでも `0` を返す。`1` は引数不正 / git エラー等の異常時のみ。
- 進捗ログ (base file count / 候補件数 / reported 件数) は stderr に出す。
  stdout は `--out` 省略時に JSON を吐くためクリーンに保つ。

### エントリポイントと bin

- `src/index.ts` の先頭に `#!/usr/bin/env node` を付け、`main(process.argv.slice(2))`
  を呼ぶ。`package.json` の `"bin": "./dist/index.js"` は既に存在するので、
  `pnpm build` 後 `npx ts-dedup ...` 相当で動くようになる。
- `tsconfig.build.json` の `rewriteRelativeImportExtensions` により `.ts` インポートは
  dist 上で `.js` に書き換わる。

### 決定性

- 各段は M1〜M6 で既に決定的に書かれている。CLI 層で新しく非決定性を持ち込まないこと:
  - `git ls-tree` の出力はあらかじめ昇順に sort する (念のため)。
  - `Map`/`Set` 反復は挿入順に依存するので、source の列挙順を固定してから index
    を作ればよい。
- `runDetector` を 2 回呼んで `JSON.stringify(report)` が一致することを
  単体テストで確認する。

### API

```ts
// src/cli/runDetector.ts
import type { Config } from "../config/index.ts";
import type { CloneCandidateReport } from "../domain/index.ts";

export interface RunOptions {
  repoPath: string;
  baseRef: string;
  headRef: string;
  config: Config;
}

export interface RunStats {
  baseFiles: number;
  baseFragments: number;
  changedFiles: number;
  changedFragments: number;
  candidatePairs: number;   // shouldReport 適用前
  reportedPairs: number;    // shouldReport 適用後
}

export interface RunResult {
  report: CloneCandidateReport;
  stats: RunStats;
}

export function runDetector(opts: RunOptions): Promise<RunResult>;
```

```ts
// src/cli/listBaseSources.ts
export interface BaseSource {
  path: string;
  text: string;
}

  repoPath: string,

): Promise<BaseSource[]>;
```

```ts
// src/cli/main.ts
export function main(argv: readonly string[]): Promise<number>;
```

```ts
// src/index.ts (rewritten)
#!/usr/bin/env node
import { main } from "./cli/main.ts";
main(process.argv.slice(2)).then(
  (code) => process.exit(code),
  (err: unknown) => {
    const msg = err instanceof Error ? err.message : String(err);
    process.stderr.write(`ts-dedup: ${msg}\n`);
    process.exit(1);
  },
);
```

## テスト

### unit: src/cli/listBaseSources.test.ts

一時 repo を使う (`test/e2e/helpers/tempRepo.ts` を共有):

- `.js` や `node_modules/**` のファイルが結果に含まれない。
- 通常の `.ts` / `.tsx` が本文付きで返る。
- path は昇順 sort されている (決定性)。
- exclude glob を `Config.exclude.globs` で足すと対象から外れる。

### unit: src/cli/runDetector.test.ts

最小の一時 repo を使ってパイプライン全体の配線を確認:

- 何も変化がない PR (base と head が同じ commit) → `candidates` 空 / `baseSha === headSha`。
- 関数 1 件コピー PR → `candidates` に期待ペアが含まれる。
- 同一入力で 2 回呼ぶと `JSON.stringify(report)` が完全一致 (決定性)。

### unit: src/cli/main.test.ts (CLI smoke)

- `main(["--repo", repo, "--base", baseSha, "--head", headSha])` が exit code 0 を返し、
  stdout で valid JSON を出す (候補 0 件でも成功)。
- `--out <file>` 指定でファイルに書き出され、stdout は空。
- `--markdown <file>` 指定で Markdown も書かれる (内容に "ts-dedup report" を含む)。
- `--help` で exit 0、stderr に usage が出る。
- 必須引数欠落で exit 1。

### E2E: test/e2e/functionCopy.test.ts

- base: `src/math.ts` に関数 `add(a, b)`。
- head: 同ファイルに変更なし、`src/util.ts` を新規追加し `add(a, b)` と同一の実装を持つ
  `addCopy(a, b)` を定義。
- `runDetector` → report.candidates に `src/util.ts` ↔ `src/math.ts` が含まれる。

### E2E: test/e2e/renameCopy.test.ts

- base: `src/validate.ts` に `validateUser(user)` (if/return + `user.id` アクセス等)。
- head: `src/check.ts` を新規追加し、`checkAccount(acc)` として同じ構造・識別子だけ変更。
- statementKindSimilarity / tokenOverlap のどちらかが threshold を超えて report される。

### E2E: test/e2e/windowCopy.test.ts

- base: `src/a.ts` にある程度長い関数 (10 文以上)。
- head: `src/b.ts` に新関数を追加し、そのうち 5〜7 文分を base のものと同じ並びにする。
- window 系の ReportCandidate が少なくとも 1 件拾われる。

### 共有ヘルパ

`test/e2e/helpers/tempRepo.ts`:

- `createTempRepo(): { repo: string; cleanup: () => void }` — `mkdtempSync` で一時ディレクトリに
  `git init -b main` し、user.email / user.name / commit.gpgsign=false を設定。
- `writeAndCommit(repo, files, message): sha` — `files` を書いて `git add -A` + `git commit`。
- テスト側は `afterEach` で `cleanup()`。

## リスク / 留意点

- **ls-tree の path エンコード**: `-z` (NUL 区切り) を使うことで quote / escape 処理を回避。
  ただし `git ls-tree` は `--name-only` 指定時に `blob`/`commit` (submodule) 等も含む。
  submodule は追加しないテストなので tree のみ来る前提で OK。将来 submodule 対応は別途検討。
- **changed file の base-side 版が index に入る**: 変更された関数は自分自身の base 版に
  強くマッチしてノイズとして現れ得る。M7 では recall 優先で追加フィルタを入れず、
  `same-file` riskFlag に任せる。M8 で再検討。
- **bin shebang と TypeScript**: `#!` は TypeScript が先頭行で黙認する。`tsc` の出力にも
  そのまま残る (`rewriteRelativeImportExtensions` とは独立)。
- **`--out` と stdout**: CI 運用では `--out` 指定が基本。stdout JSON は省略時のフォールバック。
  進捗ログは全て stderr に出す。
- **新規依存なし**: argv parse は `node:util.parseArgs`。glob は M5 の `matchesAnyGlob` を再利用。
- **テストの並列実行**: vitest はデフォルトで並列。`mkdtempSync` は一意なので競合しない。
- **大きめ fixture は test/fixtures/ に置かない**: `.gitignore` 済みの一時 repo を
  テスト内で動的生成する方針で統一。
