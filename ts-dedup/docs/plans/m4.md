# M4: Similarity Scorer (4 観点 + OR 判定)

[docs/plans/milestones.md](./milestones.md) の M4 の実装計画。

## 目的

M3 で絞り込まれた候補ペア (changed fragment × base fragment) に対して、4 観点で再スコアし、combined score を出した上で、**OR 条件**で最終的に「報告対象」を決める。

4 観点:

1. **tokenOverlap**: 正規化トークン n-gram の重なり
2. **statementKindSimilarity**: 文 kind n-gram の重なり
3. **callOverlap**: 呼び出し/プロパティ指紋の重なり
4. **sizeCompatibility**: 2 fragment のサイズ比から減点

combined:
```
combined =
  weights.token     * tokenOverlap
+ weights.statement * statementKindSimilarity
+ weights.call      * callOverlap
+ weights.size      * sizeCompatibility
```

OR 判定 (v1.md §7):
```
report if:
  combined >= thresholds.combined          (0.30)
  OR tokenOverlap >= thresholds.token      (0.35)
  OR statementKindSimilarity >= thresholds.statement (0.45)
  OR callOverlap >= thresholds.call        (0.40)
```

recall 優先。

## Approach

- **bag 比較か集合比較か**: v1 では **多重集合 (bag) としての Jaccard / Dice は扱わず、集合としての Jaccard** をベースにする。FragmentFeatures.tokens / statements / calls は重複を含む配列として持たれているが、ここでは `unique()` してから Jaccard を取る。
  - 理由: 短い fragment で少ない feature 種類しかない場合、bag 化すると極端にノイズが増える。集合ベースのほうが recall を下げずに安定する。
  - 将来 (M8) bag 版を behind a flag で提供する余地は残しておく。
- **各観点のスコアリング**:
  - **tokenOverlap** = Jaccard(unique changed tokens, unique base tokens)
  - **statementKindSimilarity** = Jaccard(unique changed statements, unique base statements)
  - **callOverlap** = Jaccard(unique changed calls, unique base calls)
  - **sizeCompatibility** =
    ```
    let a = changed 行数 (endLine - startLine + 1)
    let b = base    行数
    let ratio = min(a,b) / max(a,b)
    return ratio
    ```
    完全一致なら 1、10 倍差なら 0.1。
- **空集合の扱い**:
  - 両方空 → Jaccard は定義上 0/0 だが、`1.0` にするか `0.0` にするか?
    - token / statement: 両方空は「極小 fragment」を意味し、特徴量が出ていない → 偶然一致した扱いにすべきではない → `0.0`。
    - call: 両方空は「呼び出し無しの短い関数」もあり得るので `1.0` にすると false positive が増える → **`0.0` に統一**。
  - 片方だけ空 → 普通に Jaccard = 0。
- **combined の正規化**: weights の和が 1 前提 (defaultConfig で 0.4+0.3+0.2+0.1=1)。ユーザが和を 1 以外にしても計算は通るが、OR 閾値との解釈が崩れるので **weights の和を 1 に正規化する**前処理を combined 計算時に入れる (防御的)。
- **Evidence 抽出**: M6 で使うので、combined score と breakdown とは別に「なぜ一致と判定したか」の根拠を集める関数を M4 で提供するか、あるいは呼び出し側 (M6/M7) で extract するか?
  - M4 の責務は "score と decide" に限定する。Evidence 抽出は M6 (report generator) で行う。ただし M4 が計算中に得ている intersection 情報を捨てるのは勿体ないので、**breakdown + intersection 情報を含む詳細結果を返す関数** (`scoreCandidateDetailed`) を追加で用意する (後続段で再利用しやすくする)。
  - 基本 API `scoreCandidate` は `CandidateScore` (M0 定義) を返す。
  - Extended API `scoreCandidateDetailed` は `{ score: CandidateScore, intersections: { tokens: string[], statements: string[], calls: string[] } }` を返す。

### API

```ts
import type { Candidate, CandidateScore, Fragment, FragmentFeatures } from "../domain/index.ts";
import type { Config } from "../config/index.ts";

// 単独観点
export function tokenOverlap(a: FragmentFeatures, b: FragmentFeatures): number;
export function statementKindSimilarity(a: FragmentFeatures, b: FragmentFeatures): number;
export function callOverlap(a: FragmentFeatures, b: FragmentFeatures): number;
export function sizeCompatibility(a: Fragment, b: Fragment): number;

// 合算
export function combinedScore(
  breakdown: ScoreBreakdown,
  weights: Config["scoring"]["weights"],
): number;

// 判定
export function shouldReport(score: CandidateScore, thresholds: Config["scoring"]["thresholds"]): boolean;

// まとめ
export interface ScoreInputs {
  candidate: Candidate;
  changedFragment: Fragment;
  baseFragment: Fragment;
  changedFeatures: FragmentFeatures;
  baseFeatures: FragmentFeatures;
}

export function scoreCandidate(inputs: ScoreInputs, config: Config): CandidateScore;

export interface DetailedScore {
  score: CandidateScore;
  intersections: {
    tokens: string[];      // ソート済み
    statements: string[];
    calls: string[];
  };
}

export function scoreCandidateDetailed(inputs: ScoreInputs, config: Config): DetailedScore;
```

## テスト

### tokenOverlap.test.ts

1. 完全一致の fragment → 1.0
2. 全く一致しない → 0.0
3. 識別子だけ変えた fragment (実際には feature レベルで正規化後はほぼ同じ) → 0.7 以上を assert
4. 両方空 feature → 0.0

### statementKindSimilarity.test.ts

1. 同じ文構造 → 1.0
2. 全く違う構造 → 0.0
3. 両方空 → 0.0

### callOverlap.test.ts

1. 同じ呼び出し集合 → 1.0
2. 1/2 しか共有しない → 0.33...
3. 両方空 → 0.0

### sizeCompatibility.test.ts

1. 同じ行数 → 1.0
2. 2x 差 → 0.5
3. 10x 差 → 0.1

### combinedScore.test.ts

1. 既定重み (0.4/0.3/0.2/0.1) で breakdown = {1,1,1,1} → 1.0
2. weights 和が 2 でも正規化されて結果は同じ範囲になる (weights を [0.8,0.6,0.4,0.2] にしても combined が [0,1] に収まる)。
3. 一部 0 混じり → 期待通りの線形結合。

### decide.test.ts

1. combined が閾値未満でも token >= 0.35 なら true。
2. token, statement, call 全部 <閾値 で combined も <閾値 → false。
3. 複数観点で超えている → true。
4. 閾値ちょうど (>=) → true。
5. 閾値 - 1e-9 → false。

### scoreCandidate.test.ts

1. 既知の同一コピー 2 つの fragment で combined >= 0.9。
2. 識別子だけ変えた copy → combined は中程度、token と statement が高い。
3. `scoreCandidateDetailed` が intersections を返し、内容が両 feature の共通 key になる (決定的なソート順)。

## 受け入れ基準

- [ ] 上記ユニットテストが全て通る。
- [ ] 既知の同一コピー → 全スコア高。
- [ ] 識別子だけ変更 → token 高、statement より高。

## リスク / 留意点

- **Jaccard の偏り**: 大きい fragment と小さい fragment の比較で、小さい側がほぼ完全包含でも score が引き下がる。sizeCompatibility で緩和するが、将来 (M8) で **overlap coefficient** (intersection / min) を導入する余地を残す。
- **両方空の扱い**: 上記通り 0.0 で統一。この選択は false positive を抑える方向に倒している。
- **bag vs set**: v1 は set。bag 比較は M8 で behind flag。
- **combined の重み正規化**: defaults では和 = 1 なので正規化しても結果は同じ。ユーザ config で重みを変えた場合に備えた防御的実装。
