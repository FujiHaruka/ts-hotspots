# M5: Diff Collector + Changed Fragment Extractor

[docs/plans/milestones.md](./milestones.md) の M5 の実装計画。

## 目的

git リポジトリの **base** (ref / sha) と **head** (ref / sha) を受け取って:

1. 変更ファイル・hunk・変更行範囲を取得する (Diff Collector)
2. 変更行を含む fragment (function / block / window) を M1 の抽出器で切り出す (Changed Fragment Extractor)

重複検出の意味が無いファイル (lockfile / snapshot / migration / generated / dist / build / vendor / fixture) は除外する。`.ts` / `.tsx` 以外も除外。

## Approach

- **git 実行方法**: `simple-git` などの追加依存は入れず、**`git` を子プロセスで実行**する。理由:
  - CI では `git` 本体が必ず入っている。
  - `git diff --unified=0 --no-color --no-renames <base>..<head> -- '*.ts' '*.tsx'` 相当で十分。
  - output 形式が安定し、パーサが書きやすい。
  - `--no-renames` を付けることで rename を「削除+追加」として扱い、fragment 抽出を単純化する (recall を優先: rename 先も丸ごと changed として扱う)。
  - pathspec に `:(glob)**/*.ts :(glob)**/*.tsx` を使うと glob 解釈が統一される。
- **ファイル本体の取得**: head 側のファイル内容は `git show <head>:<path>` で得る。worktree の現在状態ではなく、head sha に固定された状態を参照する (決定性)。base 側も同様に `git show <base>:<path>` で必要に応じて取れるが、M5 スコープでは head 側だけ必要 (changed fragment 抽出のため)。
- **バイナリ・巨大ファイル**: `git show` でテキストとして読めないもの (バイナリ) は例外として捕まえてスキップ。ファイルサイズが極端に大きい (>1 MB 等) ものも除外するが、v1 では「除外 glob で落ちる」前提で厳密な上限設定はしない (YAGNI)。
- **hunk の解析**: `git diff --unified=0` の出力から以下をパース:
  ```
  diff --git a/src/a.ts b/src/a.ts
  index ...
  --- a/src/a.ts
  +++ b/src/a.ts
  @@ -12,3 +18,4 @@
  ```
  - `+++ b/<path>` で head 側の path を取る。`/dev/null` (削除ファイル) は skip。
  - `@@ -a,b +c,d @@` の `+c,d` から head 側の **変更行範囲** (1-based、inclusive) を計算する。`d` が 0 は「削除 hunk」なので head 側には行範囲が無い → 当該 hunk は skip (削除された行は head に存在しないので changed fragment として抽出できない)。`d` 省略は 1。
  - `+a,0` の形は新規追加、ではなく通常は `+<start>,<count>` の count=0 は削除のみ。新規 hunk は `+a,b` (b>0) で表現される。
  - 行範囲: `startLine = c`, `endLine = c + d - 1` (d>=1)。複数 hunk は配列で保持。
  - 同じファイルに複数 hunk がある場合は、hunk 配列として保持する。
- **除外ルール**:
  - `Config.exclude.globs` (既定は defaults.ts 参照) で fnmatch 風にフィルタ。
  - 新規 npm dependency なし、標準の `minimatch` も無しで済ませるため、**自前の軽量 glob マッチ**を書くか、`picomatch` 等の新規依存は入れない。代わりに **正規表現変換**で十分。minimatch レベルの完全互換は不要。対応するメタ:
    - `*` → 1 path segment 内の任意文字 (`/` を含まない)
    - `**` → 0..N segment
    - 完全一致も許容
  - 実装は `globToRegExp` ユーティリティに閉じ込める。
  - 除外判定は「どれか 1 件にマッチしたら除外」(OR)。
- **パスの正規化**: git が出す path は forward slash (`/`)。Windows でも git は forward slash を返す。fragment.filePath は forward slash で統一する。
- **Changed Fragment Extractor の振る舞い**:
  - 変更ファイルごとに:
    1. head 側内容を `git show` で取得 (filePath と text)。
    2. M1 の `parseSource` + `extractFragments` で **ファイル全体の fragment** を生成。
    3. 変更行範囲 (hunks の union) と **交差する** fragment だけを残す。
    4. さらに、要求通り「変更行を包含する最小 function」「包含する最小 block」「周辺 statement window」を残すため、**交差フィルタ**は十分条件 (M1 が十分な粒度で fragment を作っているため、交差するもの全部が候補)。その中から「最小 function」「最小 block」を選ぶ追加フィルタは入れず、**全交差 fragment** を返すことで recall を最大化する。
    5. 結果をファイル順・fragment 順 (M1 の順序) で返す。
- **エラー処理**:
  - `git` コマンド失敗は例外で投げる (ユーザがリポのパスや ref を間違えているケース)。
  - `git show <ref>:<path>` で該当ファイルが base 側に無い (新規) 場合は head 側だけ使えれば OK なので問題なし。
  - 非テキストは skip (warn log)。

### 型

```ts
// src/domain/diff.ts に新規追加するか、diff モジュール内部型にする。
// ドメイン横断なので src/domain/diff.ts に置き、domain/index.ts から re-export する。

export interface ChangedHunk {
  startLine: number;  // head 側 1-based
  endLine: number;    // head 側 1-based (inclusive)
}

export interface ChangedFile {
  filePath: string;          // head 側の相対パス (forward slash)
  headSha: string;           // 実際の commit sha (ref を解決した結果)
  baseSha: string;
  text: string;              // head 側のファイル内容 (UTF-8)
  hunks: ChangedHunk[];
}
```

(ChangedFile / ChangedHunk はドメイン横断なので `src/domain/diff.ts` に置き、`src/domain/index.ts` から re-export する。)

### API

```ts
export interface DiffRequest {
  repoPath: string;   // 絶対 or 相対
  baseRef: string;    // sha / branch / tag
  headRef: string;
  config: Config;
}

export function collectDiff(req: DiffRequest): Promise<ChangedFile[]>;

export function extractChangedFragments(
  file: ChangedFile,
  config: Config,
): Fragment[];

export function collectChangedFragments(req: DiffRequest): Promise<{
  baseSha: string;
  headSha: string;
  files: ChangedFile[];
  fragmentsByFile: Map<string, Fragment[]>;
}>;
```

## テスト

### globMatch.test.ts (internal)

- `dist/**` が `dist/a.js`, `dist/nested/b.ts` にマッチ。
- `**/*.snap` が `a/b/c.snap` にマッチ。
- `node_modules/**` が `src/a.ts` にマッチしない。
- 複数 glob の OR 評価。

### parseUnifiedDiff.test.ts (internal)

- 1 ファイル 1 hunk のパース。
- 複数 hunk (`@@ -x,y +a,b @@` が複数) のパース。
- 新規ファイル (`--- /dev/null` → `+++ b/...`) のパース。
- 削除ファイル (`+++ /dev/null`) は skip される。
- rename はここでは `--no-renames` 前提なのでテスト対象外。

### collectDiff.test.ts (統合)

一時 git repo を作るヘルパ (`node:child_process` で `git init` → `git add` → `git commit` を複数回) を用意し:

1. 2 commit (base / head) 間の TypeScript ファイル変更が検出される。
2. `.js` ファイルの変更は検出されない (対象拡張子外)。
3. `node_modules/` 配下の変更は除外される (exclude glob)。
4. `dist/**` の変更は除外される。
5. 新規追加ファイルが正しく検出され hunks が head 全体を指す。
6. 削除ファイルは結果に含まれない。
7. 同一入力 → 同一出力 (決定性)。

### extractChangedFragments.test.ts

- 関数全体を変更した hunk → 関数 fragment が候補に入る。
- 関数内の 1 行だけ変更した hunk → 関数 fragment + 該当ブロック fragment + 周辺 window fragment が候補に入る。
- 複数 hunk が同一関数内に当たる場合もすべて関数 fragment 1 件にまとまる (M1 が同じ fragment を返す)。
- 除外拡張子 (`.js` など) は呼び出し側 (collectDiff) で落ちる前提なのでここではテスト不要。

### pipeline.test.ts (軽い統合)

- collectDiff → extractChangedFragments の配線で、期待される fragments が file 単位で返る。

## リスク / 留意点

- **テストで一時 git repo を作る**: `node:os.tmpdir()` + `node:fs` + `execFileSync('git', ...)` で init/commit を作り、`fs.rmSync` で後始末。testfixtures はリポに含めない。並列実行時の競合に備えて `mkdtempSync` を使う。
- **git のグローバル設定依存**: コミット時 `user.email` / `user.name` を `-c` で渡して環境独立にする: `git -c user.email=test@example.com -c user.name=test commit ...`。
- **`--no-renames`**: rename 検出を無効化することで、rename されたファイルは「削除 + 追加」として扱われる。recall 優先と整合。
- **hunk 行範囲の先頭**: `@@ -a,b +c,d @@` の c は **head 側の変更が始まる行**。d=0 は「ここで削除のみ」なので head に行がない → skip。d=1 は `+<c>` 省略形 (1 行)。d>=1 で行範囲が確定。
- **glob の実装**: minimatch レベルの `?(…)` / `!(…)` / ブレース展開はサポートしない。`*`, `**`, `?` くらいで v1 は十分。
- **改行**: git が返すファイルは LF。Windows CRLF は考慮外 (CI 前提)。
- **symlink / submodule**: 除外の対象として明示されていないが、`git show` が対処してくれるのでそのまま流す (recall を下げない)。
- **大規模リポの性能**: 変更ファイルだけパースすれば十分 (base 側全ファイルは M3 の索引構築で別途スキャンされる)。
