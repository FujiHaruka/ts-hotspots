# M3: InvertedIndex + Candidate Search

[docs/plans/milestones.md](./milestones.md) の M3 の実装計画。

## 目的

base 側の fragment を M2 で feature 化した結果から「転置索引 (InvertedIndex)」を構築し、changed fragment 向けに 3 系統 (token / statement / call) の **OR 和集合**で候補検索を行う。候補ごとに系統別の hitCounts を集計し、上位 N 件を決定的な順序で返す。

## Approach

- **責務の境界**:
  - `buildInvertedIndex(fragments, features)` は「base 側 fragment と FragmentFeatures の集合」から `InvertedIndex` を作る純粋関数。
  - `searchCandidates(changedFragment, changedFeatures, index, config)` は「1 件の changed fragment + その feature」で索引を引き、Candidate 配列を返す純粋関数。
  - どちらも IO なし / 決定的。
- **索引のデータ構造**: `Map<FeatureKey, Posting[]>`。key は M2 が生成する prefix 付き文字列 (`token:...`, `statement:...`, `call:...`)。value は Posting の配列。
  - 同じ fragment から同じ key が複数出た場合は、**posting を 1 件だけ**にする (重複排除) — 索引の役割は「どの fragment がその feature を持つか」であって、bag ではない。ヒット数カウントは検索側で feature 側の出現回数を使う形にする。あるいは、posting を bag として持ち、検索側で fragment ID ごとに dedupe する。
  - v1 ではシンプルに **posting は dedupe 済み**にする: 同一 `(fragmentId, featureKey)` は 1 件のみ。その代わり「changed fragment 側の feature 出現数」と「base 側の posting 存在」を掛け算で hitCount としては使わず、**両方に出現しただけで +1 カウント**する (bag 比較は M4 のスコアリングで行う)。
- **hitCounts の意味**: `{ token, statement, call }` のそれぞれに「changed fragment の feature 集合 (重複排除) のうち、base 側にも存在したキー数」を入れる。ここが高いほど候補としての有望度が高いが、最終判定は M4 にゆだねる。
- **候補集計**:
  - changed 側 feature を `unique(tokens)` / `unique(statements)` / `unique(calls)` に分け、それぞれ index から posting を取得。
  - posting の `fragmentId` をキーに hit を集約。
  - 自己マッチ (changed fragment と同じ fragmentId) は除外する (base と changed が別集合であっても、将来 self-dedupe を含めた利用で安全)。
  - **同一ファイル内除外はしない** — base fragment 側の同一ファイルも重複候補となり得るため。
- **候補の順位付けと打ち切り**:
  - 3 系統の **OR union** なので、1 系統だけヒットした候補も残す (recall 優先)。
  - ランキングのための predicate score (M3 内部): `hitCounts.token + hitCounts.statement + hitCounts.call` の単純和。
  - 上位 N 件 (`config.search.maxCandidatesPerFragment`, 既定 100) まで残す。
  - **決定的な tie-break**:
    1. 主キー: 単純和 (降順)
    2. 第二キー: token hit 数 (降順)
    3. 第三キー: statement hit 数 (降順)
    4. 第四キー: call hit 数 (降順)
    5. 最終キー: `baseFragmentId` の辞書順 (昇順)
- **Map 反復順**: JS の Map は挿入順で安定。索引構築は fragments 配列を順に走査するので、同一入力 → 同一挿入順 → 同一反復順。検索時も走査順を固定するために feature 側も配列で持つ。

## 成果物

```
src/index_/
  invertedIndex.ts              # buildInvertedIndex(fragments, features) -> InvertedIndex
  invertedIndex.test.ts
  index.ts                      # バレル
src/search/
  candidateSearch.ts            # searchCandidates(changedFragment, changedFeatures, index, config) -> Candidate[]
  candidateSearch.test.ts
  index.ts                      # バレル
```

**ディレクトリ名メモ**: `src/index/` は `src/domain/index.ts` (バレル) や `src/config/index.ts` などファイル名との混同を招き、TS の自動補完を壊す可能性があるため `src/index_/` とする。バレル `src/index_/index.ts` がそのエントリ。

### API

```ts
import type { Fragment, FragmentFeatures, InvertedIndex, Posting } from "../domain/index.ts";
import type { Candidate } from "../domain/index.ts";
import type { Config } from "../config/index.ts";

export interface IndexInput {
  fragment: Fragment;
  features: FragmentFeatures;
}

export function buildInvertedIndex(inputs: readonly IndexInput[]): InvertedIndex;

export function searchCandidates(
  changedFragment: Fragment,
  changedFeatures: FragmentFeatures,
  index: InvertedIndex,
  config: Config,
): Candidate[];
```

## テスト

### invertedIndex.test.ts

1. 単一 fragment の feature が正しい key で登録される (`token:...` / `statement:...` / `call:...` それぞれで posting が 1 件)。
2. 2 つの fragment が同じ feature key を共有するとき、その key の posting が 2 件になる。
3. 同一 fragment が同じ key を複数回持っても posting は 1 件に dedupe される。
4. Posting の filePath / startLine / endLine / featureKind が Fragment と整合する。
5. 空入力 → 空 index (postings.size === 0)。
6. 決定性: 同一入力 → 同一構造の Map (挿入順 / 反復順まで一致)。

### candidateSearch.test.ts

1. token だけ一致する base fragment が候補として拾われる (OR の確認)。
2. statement だけ一致する base fragment が候補として拾われる。
3. call だけ一致する base fragment が候補として拾われる。
4. 複数系統で一致した場合は hitCounts が系統別に正しく集計される。
5. 自己マッチ (同じ fragmentId) は除外される。
6. `maxCandidatesPerFragment` で打ち切られる。打ち切り順序が決定的。
7. tie-break: 同じ score の候補で baseFragmentId 昇順に並ぶ。
8. 何もヒットしない → 空配列。
9. changed feature が空 → 空配列。
10. 決定性: 同一入力 → 同一配列 (順序含む)。

## リスク / 留意点

- **索引のメモリ**: v1 は CI で都度再構築する前提なので DB なしでよい (requirements.md §7)。ただし巨大リポで破綻しないか M8 で確認する。
- **feature key 衝突**: prefix (`token:`/`statement:`/`call:`) で名前空間が分離されているので問題ない。
- **ヒット「数」の定義**: 現実装は「unique feature の存在カウント」。bag 比較 (重み付き cos sim 等) は M4 で別途行う。
- **自己マッチ除外の範囲**: base と changed が同じ fragment を指すことは CI 本運用では稀だが、単体テストや将来の self-dedup 用途で保険として入れておく。
