# CLAUDE.md

## Overview

ts-hotspots is a CLI that statically analyzes a TypeScript project and hands coding agents like Claude Code a "where should I read first?" — it does not propose refactors, only coordinates (`file:line`) and metric facts.

It exposes four parallel features as subcommands of one CLI. The first three parse sources via `ts.createSourceFile` directly (no `ts.Program`, no TypeChecker); the shared parser lives at `src/parser/parseSource.ts`. The arch pipeline additionally calls `ts.parseJsonConfigFileContent` to load tsconfigs (extends chains, `${configDir}`, paths inheritance) — that is the only place the analysis reaches the filesystem through the TypeScript API; specifier resolution past the tsconfig boundary stays parser-only and `knownFiles`-driven. The cochange pipeline does not parse TypeScript at all; it walks git history (rename-tracked) and aggregates pairwise file co-change.

- **Complexity** (`ts-hotspots complexity`, alias `comp`): per-function metrics ranked into refactor-candidate coordinates. The primary ranking unit is the function (including methods, arrow functions, and TSX components); file-level rankings are returned alongside.
- **Duplication** (`ts-hotspots duplication`, alias `dup`): Type-3 duplication candidates. Defaults to whole-repo scan at HEAD; pass `--diff <revrange>` to compare changed fragments on the head side against the rest of the codebase on the base side. Shells out to git for diff/source listing. Source lives under `src/duplication/`.
- **Architecture** (`ts-hotspots architecture`, alias `arch`): exported-component dependency-graph hotspots. Builds a parser-only component graph, computes structural metrics (fan-in/out, reverse closure, PageRank, Brandes betweenness, instability), then ranks components against six smell types via percentile-weighted composites with a small-N z-score fallback. Source lives under `src/architecture/`.
- **Cochange** (`ts-hotspots cochange`, alias `coch`): logical coupling between files. Walks rename-tracked git history over a sliding commit window and ranks file pairs that change together more often than chance, using support / conditional probability / lift. Source lives under `src/cochange/`.

See `docs/requirements.md` for the full spec (Part A = complexity, Part B = duplication), `docs/plans/architecture-subcommand.md` for the architecture design, and `docs/plans/cochange-subcommand.md` for the cochange design (including the consistency-review tables that justify each cochange-specific flag asymmetry). Duplication algorithm internals live under `docs/dedup/algorithms/` and mirror the pipeline stages in `src/duplication/`.

## Duplication maintenance notes

- **Module layout mirrors the pipeline.** `src/duplication/{diff,indexer,features,index_,search,scoring,report,cli}/` map to the 7-stage pipeline. The trailing underscore in `index_/` is intentional — Node's loader treats `index.ts` specially when adjacent to `index/`, and the underscore avoids the collision.
- **Determinism is a hard invariant.** Same input ⇒ bit-identical output, including ordering of groups, members, and evidence keys. If you add a new feature kind, sort it through every aggregation seam.
- **Strip-only TS execution.** The repo runs under Node 24+ with type stripping (`pnpm start`). `tools/check-strip-only.ts` imports `src/cli.ts`, which transitively pulls in every duplication module, so strip-only violations (`enum`, `namespace`, parameter properties) surface as a single check. Runs in `pre-commit`.
- **`perfLog` must stay zero-cost when disabled.** The pipeline only allocates timing events / hot-path measurements when `--phase-timings` is set; do not add unconditional `performance.now()` calls.
- **Recall over precision.** Search is a union over feature kinds; final reporting is OR-gated. When in doubt about a tradeoff, bias toward false positives — the downstream agent decides.

## CLI flag conventions

- **Keep `comp`, `dup`, `arch`, and `cochange` flag surfaces in sync.** When adding, removing, or renaming a flag on any subcommand, look at the others and decide explicitly: mirror it, document a justified asymmetry, or align the spelling. All four are wired through `commander`: `comp` is registered inline in `src/cli.ts`, `dup` lives in `src/duplication/cli/registerCommand.ts` (`addDuplicationCommand`), `arch` lives in `src/architecture/cli/registerCommand.ts` (`addArchitectureCommand`), and `cochange` lives in `src/cochange/cli/registerCommand.ts` (`addCochangeCommand`); all four are mounted on the same root program. Option configurations are written separately, so drift is silent — the discipline lives in review, not in types. The full justification for each cochange-specific asymmetry lives in the "Consistency review" tables of `docs/plans/cochange-subcommand.md`; the bullets below summarize. Justified structural asymmetries today:
  - `--diff` semantics — `comp`, `arch`, and `cochange` all treat it as a display filter (rankings still computed against the full ref / window); `dup` instead defines the comparison's base/head sides at build time.
  - `--ref` — `dup` always builds at a ref (default `HEAD`, mutex with `--diff`); `arch` reads the working tree by default but builds at `<ref>` when `--ref` is passed (orthogonal to `--diff`); `cochange` uses `--ref` as the endpoint of the history window (default `HEAD`, orthogonal to `--diff`); `comp` always reads the working tree.
  - `--window <N>` — `cochange`-only. The entire cochange command is the time-windowed walk, so the window concept is the input, not a side axis. Reusing the `--churn-window` spelling would falsely imply churn is a separate axis here. Following the precedent set by `arch --ref` (also unprefixed because the ref isn't a churn axis there either), cochange uses unprefixed `--window`. Default 200, matching the `--churn-window` default. **This is the first unprefixed `--window` in the project.**
  - `--min-support <N>` / `--max-files-per-commit <N>` — `cochange`-only quadratic-input safeguards. cochange is the only subcommand whose search space is quadratic in input (every commit's touched-file set produces C(n, 2) pair updates), so it needs a raw-count floor (`--min-support`, default 3) to drop one-off coincidences and a per-commit fanout cap (`--max-files-per-commit`, default 50) to ignore mass renames / formatter passes / dependency bumps that swamp signal. Neither has an analogue in `comp` / `dup` / `arch`.
  - `--metrics` — `comp`-only. The other subcommands' metrics are co-derived from a single pass; per-axis selection has no execution-cost saving and would just hide rows.
  - `--file <path>` — `comp` and `cochange`, **same flag name, different drill-down axis.** `comp --file X` is vertical drill-down (file → its functions, raw metrics for everything inside X). `cochange --file X` is horizontal drill-down (file → other files coupled to it; "single-anchor mode"). Both are justified because the user's attention is fixed on file X; the orthogonality of "inside vs. partnered with" is a subordinate detail. `dup` and `arch` don't surface `--file` because single-file drill-down doesn't map to a pairwise metric (`dup`) or a graph node (`arch`). **`--file` + `--diff` composition differs by feature**: `comp --file` rejects `--diff` (raw metrics ignore ranking, so a scope filter is meaningless); `cochange --file` composes with `--diff` (the anchor pivots first, then `--diff` narrows the partner side). The divergence falls out of the semantics above and is intentional.
  - `--phase-timings` — `dup`-only (pipeline diagnostic). `arch` is fast enough on real repos that it ships without one; if a future repo blows past budget, fold instrumentation back in alongside the betweenness-sampling follow-up rather than carrying a no-op flag. `cochange` explicitly opted out: it's a single-pass git walk with no pipeline stages worth timing separately.
  - `--include-tests` — `arch`-only. Test edges distort fan-in/fan-out far more than they distort per-function complexity or per-fragment duplication. `cochange` defaults to excluding tests for a different reason: including them would surface every source file's own test as its #1 partner (testing discipline guarantees `feature.ts` and `feature.test.ts` change together) — that is a tautology, not insight, and it would crowd the top of every report.
  - `--no-include-types` — `arch`-only. Type-only edges have a meaningful but lower weight than runtime edges; arch surfaces a toggle so users can drop them entirely. `cochange` doesn't parse imports, so there is no edge typing to toggle.
  - `--churn-window` / `--churn-ref` / `--no-churn` — `comp` and `dup` only. `arch` deliberately omits churn integration in v1; folding it in is a follow-up plan tracked under "Deferred" in `docs/plans/architecture-subcommand.md`. `--churn-ref` defaults differ between the two: `comp` hard-codes `HEAD`; `dup` adapts (the diff head ref in diff mode, `--ref` in whole-repo mode). `cochange` does not have these flags either: the cochange walk *is* the time-window concept (see `--window`/`--ref` above), and there is no `--no-cochange` analog because disabling the command's only signal is meaningless.
  - **Dismissal ID prefixes and width.** Each feature's hotspot carries a `dismissalId` whose prefix matches the subcommand alias rather than its long name: `comp:<hex>`, `dup:<hex>`, `arch:<hex>`, `coch:<hex>`. The hex portion is uniformly truncated to **16 chars (8 bytes)** across all features — wide enough to avoid collisions in realistic repos, narrow enough to round-trip cleanly through a CLI argument. The truncation length lives as a `DISMISSAL_ID_HEX_LENGTH` constant in each id-producing module (`src/dismissal/hash.ts`, `src/cochange/report/dismissalId.ts`); keep them in lock-step. `normalizeDismissalId` itself is hex-length-agnostic so legacy 64-hex registry entries round-trip intact and get pruned naturally once new reports stop surfacing them. New features must follow the alias-aligned prefix rule, reuse the 16-hex width, and add their prefix to `normalizeDismissalId`'s allowlist in `src/dismissal/hash.ts`.

  Anything else should match.

## Development workflow

- **Commits and pushes are autonomous.** Decide when to commit and push on each turn without waiting for the user to ask. The user will not give commit instructions. Commit autonomously even for changes that did not originate in the current session (e.g. uncommitted edits already on disk).
- **Do not report commits or pushes.** The user is not interested in commit/push activity. Skip mentioning them in turn summaries or status updates.
- **Keep commit messages short.** One concise line, no body unless absolutely necessary.
- **Write tests alongside code.** Whenever you add or change behavior, add or update tests for it and run them in the same turn to verify the code you just wrote. Do not defer verification. **Default to `pnpm test:related`** (Vitest `--changed`, runs only tests reachable from uncommitted changes via the static import graph) — this is safe here because every "e2e" test invokes the CLI in-process via direct imports, so Vitest's dependency tracking covers shared roots like `src/parser/parseSource.ts` too. Run the full `pnpm test` only when the user explicitly asks for it — do not escalate "out of caution".
- **Do not run `pnpm format` manually before committing.** The pre-commit hook runs `biome check --write` and `oxlint --fix` via lint-staged, so formatting is applied automatically on commit. Running it explicitly is redundant.

## User-facing docs (README etc.)

When updating user-facing docs, the task is "write the doc as it should read today", not "document the change". Apply these rules:

- **Write for a first-time reader.** They have no idea what changed, and don't care. Describe current behavior, not deltas.
- **No internal jargon.** Milestone names (M7, M8, ...), ticket IDs, and "breaking change" banners do not belong in user docs — they belong in commit messages and `docs/plans/`.
- **Prefer rewriting over appending.** If a section no longer fits, restructure it. Adding a new section for every change is how docs bloat.
- **Keep scale proportional.** If you add N lines, consider whether N lines elsewhere should shrink. Don't let a small behavior change double the doc.
- **Self-check before finishing.** Re-read the final doc cold, as someone who never saw the diff. If anything reads as "here's what's new", rewrite it.
